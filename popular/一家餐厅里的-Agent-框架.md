# 一家餐厅里的 Agent 框架：从大酒楼到一块空铺面

> 一篇关于 DeepSeek Harness 架构的科普。不写代码，只讲一家餐厅的故事。
> 如果你读完想去翻源码，技术向的逐层教程在隔壁 [learn/](../learn/README.md)。

## 一、城里最热闹的酒楼

城南有家酒楼，叫**深见楼**。生意好到什么程度？店里同时运转着 **95 个岗位**：迎宾、点菜、传菜、灶台、面点、冷盘、收银、采购、仓管、安保、记账、分店联络员……

这家酒楼有个古怪之处：**没有老板，也没有经理办公室。** 店里只有两样东西是"固定资产"：

1. 一块铺面，和一套写在墙上的**《店内规矩》**；
2. 一块大公告栏，任何人上岗、离岗、喊话，都走这个公告栏。

95 个岗位全是"挂"在这套规矩上的。挂得多了，是今天的大酒楼；挂得少，可以是街角的便当店。铺面和规矩从不变，变的只是**排班表**。

如果你把"酒楼"换成"AI Agent 产品"，把"岗位"换成"插件"，你已经理解了 DeepSeek Harness 的八成。下面把这个故事讲完。

## 二、一个疯狂的实验：裁员裁到只剩规矩

有天打烊后，掌柜做了个实验：**一层层裁掉岗位，看酒楼什么时候才"不是酒楼"。**

**第一刀：砍掉门面。** 把雕花门头、等位沙发、扫码点餐屏全拆了——这些是"客人从哪进来"的事。酒楼还是酒楼，只是少了种进店方式。

**第二刀：砍掉特色服务。** 分店联络、餐后甜点推荐、会员卡、今日特惠……全撤。酒楼居然还能开：客人照样点菜、吃饭、买单，只是"不那么周到了"。

**第三刀：砍到只剩厨房底线。** 掌柜发现，一家能开张的"最小店"只需要九个岗位：一位动嘴不动手的顾问、一位记存根的、一位管店规的、一套厨房设备、一位领班，再加几个打杂的。街角那家 32 个岗位的便当店，就是活的证据。

**最后一刀：全裁了。** 铺面空了。剩下什么？

> 不是灶台，不是账本，甚至不是"餐厅"两个字——只剩下**公告栏和那套《店内规矩》**。

这就是整个实验的结论：**一家餐厅的本体不是任何一个岗位，而是"岗位如何上岗、如何协作、如何离岗"的制度本身。** 在 Harness 里，这套制度叫 Cordis——一个插件框架。它不知道什么是 AI、什么是模型，正如《店内规矩》不知道什么是东坡肉。

## 三、《店内规矩》只有五条

整套制度就五条规矩，所有 95 个岗位都靠它运转。

**规矩一：每个人只带一张岗位说明上岗。**
说明上写着"我负责什么"。至于店里还有谁、整体怎么运转，不需要知道。（在框架里，这张说明叫**插件**。）

**规矩二：喊岗位，不喊人名。**
"收银！3 号桌买单！"——没人喊"小张！"。公告栏上谁挂了"收银"的牌子，谁就应声。小张请假换小李，全店无感。（公告栏叫 **Context**，牌子叫**服务**。这就是为什么"换供应商"在 Harness 里只是换一行配置：牌子一摘一挂，喊话的人根本不知道。）

**规矩三：你的搭档没到，你就等着。**
传菜员的说明上写着"搭档：灶台"。灶台没点火，传菜员就在旁边候着——开工顺序由**搭档关系**决定，不是谁打卡早就谁先上。而且这是持续盯着的：灶台中途熄了，传菜员自动下岗；火一着，他又回来。（这叫 **inject 依赖声明**。）

**规矩四：喊话分两种。**
- **广播**："3 号桌买单了！"喊的人不关心谁听见，该动的岗位自己动。（`emit` 事件。）
- **流水线**：一张订单从迎宾→点菜→厨房，每个环节可以添一笔（"少盐"），也可以当场把单子拦下（"卖完了"——后面环节不用走了）。铁律：**只过手不决定的环节，必须盖个"已阅"传给下一站**，忘了盖章，后面所有人干瞪眼。（这叫 `waterfall`，盖章就是 `next()`。Harness 里的"工具审批""模型请求拦截"全是这种流水线。）

**规矩五：离岗即复原。**
任何人下班，他挂的牌子、他登记的"我负责 X"、他贴的便签，**自动全部摘掉**，公告栏回到他来之前的样子。（这叫 **effect**：一切注册皆可逆。这就是为什么裁员实验能做得这么干净——从来没有"拆不掉的装修"。）

## 四、把酒楼一层层开回来

现在反着走：一块空铺面，一套规矩，怎么把大酒楼开回来？每加一层，店就"更像样"一分。

**先请一位顾问（模型层）。** 这位顾问嘴皮子极厉害，但**从不动手**——他只说"该做什么"。而且顾问可以换：今天请川菜的，明天请粤菜的，只要在公告栏挂"顾问"的牌子，全店照样喊"顾问！"。（`ctx.llm` + 可替换的模型适配器。）

**立一个规矩：存根为凭（会话日志）。** 顾问每吩咐一道菜、厨房每出一道菜，都必须记点菜单存根。**"上过什么菜，以存根为准，不以任何人的记忆为准。"** 有了存根，才能查账、能复盘、能分店继承老客人的口味。（事件溯源：模型看见的一切，必须先落进会话日志。）

**贴一墙店规（系统提示词）。** 店规不是一张死告示，而是每个岗位都可以往墙上贴一条：迎宾贴"今日客满"，大厨贴"例牌是白切鸡"，按固定顺序拼成一整面墙。顾问开口前，先看这面墙。

**配厨房设备（工具注册表）。** 顾问动嘴，设备动手。每样设备挂一张使用说明贴到墙上（顾问看得到才知道有它）；每次动用设备，固定走一道流程：大堂经理先审（危险操作要问客人）→ 开火 → 出品 → 记存根。

**请一位领班（代理循环）。** 到此，店终于"转"起来了：领班接单→把存根和店规递给顾问→顾问吩咐→指挥设备→记存根→直到这桌再不欠任何菜。九类岗位，就是那家 32 岗便当店的全部。

**剩下的，都是锦上添花。** 后厨扩建（炉灶区、安全护栏、储物间）；账本房（每晚把存根誊进只添页、不改页的账本）；分店体系（派一位领班去支援新店，他还是用同一套规矩）；翻台精简（忙了一晚，把冗长的存根整理成摘要）……每一种"高级服务"，拆开看都只是**前四条规矩的排列组合**——没有一个需要修改《店内规矩》本身。

**最后，同一批员工，开四种店。** 大酒楼（网页版）、外卖窗口（命令行一次性任务）、中央厨房（SDK）、团餐专线（ACP）——区别只在**排班表**：哪 95 个岗位、谁上谁歇（歇岗不是开除，表上画个叉，随时画回来）。而街角那家 32 岗便当店倔强地证明：不用大酒楼的排班表，最小配置也能开张。

## 五、对照表：餐厅 ↔ Harness

| 餐厅里 | Harness 里 | 一句话 |
|---|---|---|
| 公告栏 | `Context`（ctx） | 一切注册与查找的总线 |
| 岗位说明 | 插件 `apply(ctx)` | 只声明"我贡献什么" |
| 岗位牌子（收银/顾问） | 服务 `ctx.llm`、`ctx.tools` | 喊岗位不喊人名，换人即换实现 |
| "等灶台点火才开工" | `inject` 依赖声明 | 顺序由依赖驱动，不由排队先后 |
| 广播 | `emit` 事件 | 宣布事实，不关心谁听 |
| 订单流水线（可加工/可拦截） | `waterfall` 事件 + `next()` | 过手必须盖章，拦截即短路 |
| 离岗自动摘牌 | effect 可逆注册 | 所以裁员（减法）干干净净 |
| 点菜单存根 | 会话日志 `ctx.sessions` | 上桌的每道菜必须有存根 |
| 一墙店规 | `ctx.systemPrompt` 分段装配 | 每个岗位贴一条，按序拼合 |
| 厨房设备 + 大堂审批 | `ctx.tools` 五段管线 | 动设备先审批，出品必记存根 |
| 领班 | `ctx.agentLoop`（turn/step） | 接单→顾问→设备→存根，直到不欠菜 |
| 排班表 | `cordis.yml` / patch / profile | 95 岗酒楼与 32 岗便当店只差一张表 |
| 铺面 +《店内规矩》 | Cordis 框架（vendor/cordis） | 全部裁光后剩下的东西 |

## 六、三个容易望文生义的误解

讲完故事，顺手拆掉三个最常见的误读——它们几乎每个第一次接触这套架构的人都会踩。

**误解一："插件多 = 系统重。"**
95 个岗位的大酒楼，并不比 32 个岗位的便当店"笨重"。没挂上岗的牌子不占任何成本——它们只是货架上的可选项。真正决定店有多"重"的，是**此刻激活了多少协作**，不是**最多能激活多少**。所以"功能丰富"和"轻量"在这套架构里不矛盾：同一份代码，便当店和大酒楼随你挑。

**误解二："框架嘛，总有个总管一切的 main。"**
深见楼没有老板办公室。翻遍 Cordis 的 9 个源文件，你找不到任何"主管"：没有模型、没有工具、没有 Agent——连那个看起来最像主角的"领班"（agent-loop），也只是挂在公告栏上的一个普通插件，换个排班表他就不在了。**主干上什么都没有，正是这个框架全部的主干。**

**误解三："做减法 = 删代码。"**
歇岗不是开除。实验里的每一次"砍"，只是在排班表上画了个叉（`disabled: true`），下层的排班文件一个字节都没动——所以任何一刀都能随时画回来。这就是为什么这套系统的定制是**可逆的注记**，而不是**不可逆的手术**。

## 七、30 秒电梯演讲

如果只能向朋友复述一段话，就用这个版本：

> "我研究了一个 AI Agent 系统，发现它像一家没有老板的餐厅：近百个岗位全部挂在一块公告栏上，每人只看自己的岗位说明，别人喊岗位不喊人名；搭档没到就等着，下班自动摘牌复原。所以这家餐厅可以一层层裁员到只剩空铺面和五条规矩，再一层层开回来——开成酒楼、外卖窗口还是中央厨房，区别只在一张排班表。所谓架构，不是楼里的任何一件家具，而是'东西怎么挂上去、怎么摘下来'的制度本身。"

## 八、这个故事为什么值得程序员细品

很多框架的"扩展"是往主干上打补丁：改一处，动全身。而深见楼的答案是：**主干上什么都没有，一切都在公告栏上挂着。** 于是三件难事变成了日常：

- **减法容易**——歇岗不拆店，画个叉而已（实验中 95 岗裁到 9 类，店照开）；
- **替换容易**——喊岗位不喊人名，换顾问、换炉灶供应商，全店无感；
- **叠加容易**——新服务永远是"贴一张便签到已有的公告栏/流水线"，从不需要改写《店内规矩》。

下次再看到一个 60 多个包、近百个插件的项目发怵时，不妨想想这家酒楼：**先找到那块公告栏，再顺着排班表，一个岗位一个岗位地看。** 你会发现没有什么是不可理解的——它们只是 95 张岗位说明，挂在同一套五条规矩上。
